# Ala — Stage 7: Local Face Recognition Engine (EXPERIMENTAL)

## Scope and hardware
Stacked on PR #42 (`feature/ala-personal-memory-engine-stage6`), **not** PR #39/40. No merge into main. ESP32-P4 GUITION + built-in OV02C10 camera; ESP-IDF 6.1, 16 MiB flash; existing Xiaozhi unchanged.

This stage introduces actual Espressif ESP-DL on-device detection (`MSRMNP_S8_V1`) and feature extraction (`MFN_S8_V1`) on original camera RGB pixels, rather than assigning a name whenever a face appears. Registry dependencies: `espressif/human_face_recognition ==0.3.3` and transitively `espressif/human_face_detect ~0.5.0`. Default model location is flash **RODATA**, not SD. Both models are vendor-supported on ESP32-P4. Their sources and licenses come from the vendor's MIT-licensed model components; the ESP-DL engine may have its own declared license (verify packaged dependencies during build). No external face recognition API, server, Raspberry Pi, computer, independent TTS/STT/LLM.

Official Espressif reference ESP32-P4 figures (not measurements of Ala): MFN_S8_V1 recognition 112×112×3, 1.2 million parameters, approx. 2.1ms preprocess + 81.5ms model; MSR+MNP face detector 120×160×3 first stage + 48×48×3 second stage, approx. 17ms across preprocess/model and one candidate. These reference configurations use P4 400 MHz, L2 256 KiB and PSRAM 32 MiB at 250 MHz; our P4 board may differ. Real application flash size, free internal RAM, PSRAM and latency must be measured by CI + hardware. Source: official Espressif esp-dl model README files in `models/human_face_recognition` and `models/human_face_detect`.

## One camera owner and priority
The camera stays owned by existing `hb_camera` and `EspenVision()`. The background face worker acquires only a normal `hb_camera_acquire` **lease** and always releases it after copying a downscaled RGB888 frame. It never changes CSI/ISP drivers or owns a second sensor, and never holds a lease through inference. Worker checks that the system is idle, not in "bez odbioru", and `EspenVision().Activity()==0`; a requested Xiaozhi photo or normal speech takes priority. Rendering is always on the existing LVGL task. A lower priority FreeRTOS worker processes at most ~1 frame per 900ms and drops frames while previous inference is running. PSRAM workspace buffer is 240×320×3 = 230,400 bytes. Stack request is 12,288 FreeRTOS stack units as interpreted by ESP-IDF. No additional frame queue is introduced.

## Explicit enrollment and opt-in
In existing PIN-protected local phone panel select **📷 Rozpoznawanie domowników**, check consent (for a child: parent/guardian), enter a name, choose **Zbieraj próbki**. Runtime looks for exactly one face and extracts a *real MFN feature vector* from four different valid frame sequences. It rejects no face, multiple faces, identical sequence, invalid embedding, poorly exposed/featureless frames, and invalid input lengths. Select **Zatwierdź profil** to create it. **Anuluj** abandons pending samples. At most five named profiles. The permanent feature (in this experimental stage) is optional; default state is OFF each boot. Model loads only after explicit activation or enrollment.

Enable recognition separately. Each frame produces `NO_FACE`, `UNKNOWN`, `CANDIDATE`, `RECOGNIZED`, `UNCERTAIN`, `MULTIPLE_FACES` or `ERROR`. Vectors are L2-normalized. Cosine similarity is **not a probability**. Experimental provisional gates are 0.65 minimum cosine, a 0.10 best-vs-second margin, and three consecutive consistent matches; these MUST be calibrated with real captures (FAR/FRR) before use outside an experiment. Ambiguity resolves to `UNCERTAIN`, never guessing a name; an unknown face is never automatically enrolled. Cooldown of 90 seconds avoids greeting spam. A correct opt-in match triggers **only a 4-second visual greeting** and an existing `AlaBehaviorEngine::SocialReaction(Greeting)`, never bypasses sticky phone emotions or the Stage 5 Xiaozhi autonomy safety gate. No TTS/extra audio.

## Privacy and persistence
Embeddings, names, temporary sample vectors are held **only in volatile RAM**. They are not persisted in unencrypted NVS or any file, exported via HTTP, included in `.alamemory`, included in logs or uploaded to cloud. Clearing a profile or resetting the device removes volatile data; deletion best-effort overwrites embedding floats. This stage explicitly **does not claim encrypted persistent profiles**: no verified NVS Encryption/Flash Encryption provisioning or secure key lifecycle on the target. The phone's `/api/face` GET exposes only metadata and name/ID to a PIN-authorized browser; POST supports `on/off/begin|YES|name/commit/cancel/delete|id/clear|POTWIERDZAM`. Existing phone HTTP is **unencrypted**, so operate only on trusted LAN and do not expose this service to the public Internet. Facial recognition is **not authentication** and does not allow memory access or administrative actions. A photo presented to camera may fool the recognition model; no liveness/spoof resistance is claimed. Avoid enrolling bystanders.

## Automated and physical verification
`tests/test_ala_face_recognition.cc` uses synthetic deterministic feature vectors only to cover consent refusal, bounded registration, sample sequence, normalize invalid vector, repeated recognition, unknown, ambiguous pair, 90s cooldown, delete/clear and memory reset. `tests/test_ala_face_contracts.py` verifies API PIN route and model/kernel source links. Existing regression suite includes Xiaozhi, barge-in, standby, photo capture, emotional phone commands and Stage 6 memory. Host-only test doubles **do not prove** successful face recognition on actual humans. GitHub Actions Stage 7 should run complete ESP32-P4 IDF 6.1 build, verify app partition maximum `0x3f0000`, flash image <= 16 MiB, and `espen.bin` / SHA256. If models don't fit, do not publish firmware or silently change layout.

### Test checklist on physical Ala — NOT TESTED until executed
- Explicit consent, enroll adult profile with four distinct well-lit frames; verify status, PIN, cancellation and 5-person limit.
- Walk away and back: verify `CANDIDATE` then `RECOGNIZED` and a correct visual greeting. Repeat under day, evening, low/bright light, glasses and angled head.
- Another unenrolled family member: must never be misnamed. Compare two similar looking people and test multiple visible faces. Calibrate false accept and false reject rates before shipping.
- Show a photo of known person on phone to test spoofing. **Do not** use as access control.
- Delete one and all; switch off; reboot: verify all biometrics vanish (RAM-only). No image/biometric API payload/log/traffic.
- While repeatedly previewing and capturing Xiaozhi photos, talk, interrupt speech, speak wake word, enter/leave "bez odbioru", and set a persistent emotion from phone. No regressions or extra voice replies.
- Run for >=30 minutes with status logs: CPU, free RAM/PSRAM, high-water mark, task runtime, camera dropped frames, inference timings, temperature (if sensed), LVGL touch latency, voice stability and zero unexpected resets. Validate offline operation of face model itself (Xiaozhi speech remains online-dependent).
